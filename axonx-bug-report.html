axonx/config/default.yaml:6-10 · axonx/components/service/http/plugins.py:41-48 · components/plugin/local/manager.py:24-36, 76-85 · constants.py:25
机制

任务成功结束后，磁盘状态被改写为 failed

axonx/components/task_manager/local/manager.py:210-219 · 关联 index.py:33-45, 140-155；config/default.yaml:12-20
机制
_handle_worker_exit 判断「worker 有没有写最终状态」时，读的是 await self._index.snapshot() —— 内存索引，而不是磁盘上的 status.json。 而 worker 是独立子进程（runner._publish 直接写文件），父进程的索引只能通过 watchfiles 观察磁盘变化来更新。TaskProcessSupervisor._monitor 在 process.wait() 返回后立刻回调 on_exit（process.py:118）， 此时索引还停留在 running —— 于是终态被覆盖成失败。
触发
任何运行时间超过索引可见窗口的任务，正常退出。默认配置（debounce=60000, step=3000, poll_delay_ms=3000）下实测索引落后磁盘 约 5–6 秒；测试用的 poll_delay_ms/step = 50 几乎无延迟，所以测试全绿而生产全红。 
index observed running after 6.1s
worker exit code: 0
disk at exit: succeeded
FINAL disk state: failed | exit_code=1 | error=Worker exited without final status (code 0)
返回码 0 的正常退出被写成 exit_code=1，错误信息还宣称「没有写入最终状态」——而文件里明明写着 succeeded。

这是本次未提交改动引入的回归。旧版 awatch(debounce=200, rust_timeout=1000, yield_on_timeout=True) 实测事件延迟 0.0s，新版同样的测量下默认配置要 5.0s：

watcher 配置status.json 变更被索引观察到
旧版 debounce=200, rust_timeout=1000, yield_on_timeout0.0 s
新版默认 debounce=60000, step=3000, poll_delay_ms=30005.0 s
连带
同一个过期快照还让 delete()（manager.py:181-182）拒绝删除已经成功的任务、 cancel()（:157）对已结束任务返回 False； _mark_dead_tasks（:91）重新读的也是索引而非磁盘，因此只会与过期记录自洽。
修复
在 _handle_worker_exit 与 _mark_dead_tasks 里，判定前先 await self._index.refresh(task_id)（或直接读 status.json）。 调小 step/poll_delay_ms 只能缩小窗口，关不掉它。

H1 High

ShellStep 超时后永久挂死，连取消也一起卡住

axonx/steps/common/shell.py:26-39
机制
超时分支先 _kill_process_group()，紧接着 await process.communicate() ——这次等待没有任何超时。若命令留下了脱离进程组的子进程（setsid() 或自行 daemon 化）且仍持有继承来的 stdout/stderr 管道，communicate() 会一直等 EOF，永远不返回。CancelledError 分支（:38）是同样的写法。 
command = python -c "os.setsid(); time.sleep(30)" & sleep 30   # timeout 设为 0.5s
STILL HUNG after 12s -> step never returns
连外层 wait_for(step(ctx), 12) 都没能打断它——取消会触发 CancelledError 分支， 而那里同样是无超时的 communicate()，于是取消操作本身也挂死。 附带：超时分支把已经产生的输出丢弃了（"stdout": ""）。
修复
第二次等待加短超时（asyncio.wait_for(process.communicate(), 1)），超时后 process.kill() 收尾，并保留已读到的部分输出。
H2 High

Application._close 用 except Exception，与 _start 的 BaseException 不对称，导致组件泄漏

axonx/core/application.py:45-53 · 对比 :35
机制
_close 先 self._started.pop() 再从列表中移除组件，然后才调用 close()，且只收集 Exception。asyncio.CancelledError 属于 BaseException，一旦抛出就打断整个 while 循环——而那个组件已经出栈， 再没有任何重试机会。框架自身的 BaseComponent.close() 是故意把 BaseException 收集后再抛的（components/base.py:125-132）， 所以这类异常确实会抵达这里。 
[normal RuntimeError ] raised ExceptionGroup; closed=['first', 'second', 'third']
[asyncio.CancelledError] raised CancelledError; closed=['first']
普通异常下三个组件都被关闭；换成 CancelledError 就只有第一个被关， 其余（子进程 supervisor、文件监听 index、HTTP client）永不关闭——子进程、watcher、socket 泄漏，进程可能无法退出。
修复
与 _start 对齐改为 except BaseException，或捕获 CancelledError 后继续循环、最后用 BaseExceptionGroup 抛出。
